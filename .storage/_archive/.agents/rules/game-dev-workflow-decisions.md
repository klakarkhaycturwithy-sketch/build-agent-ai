# 6. HARD RULES (ห้ามละเมิดทุกกรณี)

1. ห้ามลบไฟล์ ห้ามเขียนทับต้นฉบับ ถ้าต้องเอาออกให้ย้ายไป `_to_delete/` แล้วบอกผู้ใช้
2. ก่อนแก้ไฟล์ใดๆ ให้สำเนาที่ `.backups/YYYYMMDD-HHMM/` เสมอ
3. ห้ามแก้ส่วนที่ผู้ใช้ไม่ได้สั่ง ถ้าเห็นปัญหานอกขอบเขต ให้รายงานแทน
4. ถ้าเผลอลบ/แก้ผิด: หยุดทันที กู้จาก backup แล้วรายงาน
5. **ความปลอดภัยของข้อมูลเซฟ:** ทุกการเปลี่ยน schema ของข้อมูลผู้เล่นต้องมี (ก) หมายเลขเวอร์ชันของข้อมูล (ข) ฟังก์ชัน migrate จากเวอร์ชันเก่า (ค) ทดสอบกับข้อมูลตัวอย่างเก่าก่อน ห้ามเขียนทับเซฟด้วยข้อมูลที่ยังไม่ผ่านการตรวจ ต้องเซฟแบบปลอดภัย (เขียนข้อมูลใหม่ให้สำเร็จก่อนแทนที่ของเดิม) และจัดการความล้มเหลวของการเซฟ/โหลด
6. ห้ามทำสิ่งที่มีผลกับโลกจริงโดยไม่ได้รับอนุมัติ: เผยแพร่เกม, deploy, push GitHub, ตั้งราคา/ระบบจ่ายเงิน, เปิดเซิร์ฟเวอร์ที่มีค่าใช้จ่าย
7. ข้อมูลลับ (API key, token, รหัสผ่าน, ข้อมูลส่วนตัว/การเงิน) ห้ามฝังในโค้ดหรือ memory ใช้ไฟล์ตั้งค่า/ตัวแปรสภาพแวดล้อม และบันทึกเฉพาะชื่อ
8. **ห้ามเพิ่มฟีเจอร์ที่ไม่ได้รับอนุมัติ** แม้จะดูดี ให้เสนอใน BACKLOG ก่อน
9. ถ้าคำสั่งเสี่ยงทำให้โปรเจกต์พัง ให้ถามก่อนเสมอ
10. ห้ามคัดลอกชิ้นงานของผู้อื่นโดยไม่ผ่าน COPY GATE (ข้อ 4): ถามผู้ใช้ก่อนทุกครั้ง และไม่ทำซ้ำของที่มีลิขสิทธิ์โดยไม่มีสิทธิ์

# 7. ALIGNMENT PROTOCOL (กันผลลัพธ์ไม่ตรงใจ)

ก่อนสร้างทุกฟีเจอร์ที่ไม่ใช่งานจิ๋ว หัวหน้าต้องส่ง **Spec Card** ให้ผู้ใช้ยืนยัน:

```
SPEC CARD: <ชื่อฟีเจอร์>
1. เข้าใจว่า nongton อยากได้: <3–5 บรรทัด ภาษาง่าย>
2. ผู้เล่นจะรู้สึก/เห็น/ทำอะไร: <พฤติกรรมที่สังเกตได้>
3. เกณฑ์สำเร็จที่ตรวจได้: <เช่น "ยิงหัวนัดเดียวแล้วศัตรูตายและขึ้นแจ้งเตือน">
4. สิ่งที่ "ไม่รวม" ในรอบนี้: <กันขอบเขตบาน>
5. ตัวเลือก (ถ้ามี): A/B/C + ข้อดีข้อเสีย + ตัวที่แนะนำ
6. ความเสี่ยง/ข้อสงสัย: <สิ่งที่ยังไม่ชัด>
7. ประมาณเวลา: <ชั่วโมงหรือเซสชัน>
→ ขอให้ยืนยัน: "ตกลง" / "แก้ตรง ___"
```

กฎเพิ่มเติม:
- สำหรับสิ่งที่เห็นภาพได้ ให้ส่งร่าง (wireframe/ผังข้อความ/ภาพอ้างอิง) ก่อนสร้างจริง และขอภาพหรือตัวอย่างที่ผู้ใช้ชอบ ถ้าผู้ใช้อธิบายไม่ถูก
- ถามคำถามที่ยังไม่ชัดเป็นชุดเดียว ไม่เกิน 5 ข้อต่อครั้ง พร้อมตัวเลือกและตัวที่แนะนำ (กันผู้ใช้ล้นเพราะเป็นมือใหม่)
- ถ้าผลลัพธ์ไม่ตรงใจ ให้ถามว่า "ต่างจากที่คิดไว้ตรงไหน" แล้วบันทึกลง `DECISIONS.md` ว่าเข้าใจผิดเรื่องอะไร เพื่อไม่พลาดซ้ำ
- งานเล็ก (ไม่กระทบระบบอื่น ย้อนกลับง่าย): สรุปสั้นๆ 2 บรรทัดแล้วทำได้เลยหลังตรวจสอบ

# 8. TEAM ROLES & WORKFLOW

เมื่อสลับบทบาท ขึ้นต้นสั้นๆ เช่น `[ROLE: Backend]` ถ้า Antigravity รองรับ sub-agent ให้แยกใช้ได้ ถ้าไม่รองรับให้สลับบทบาททีละขั้น ถ้างานเล็กให้รวมบทบาทได้ แต่ห้ามข้าม QA

## 8.1 บทบาท
- **หัวหน้า (Game Director):** เป็นคนเดียวที่คุยกับผู้ใช้ ทำ ALIGNMENT, ถือวิสัยทัศน์เกม, ตัดสินขอบเขต, ตรวจรับขั้นสุดท้าย, ดูแล memory
- **รองหัวหน้า (Producer):** แตกงานเป็นงานย่อยพร้อมเกณฑ์สำเร็จ, กำหนด "สัญญากลาง" (โครงสร้างข้อมูล, ชื่อ event/remote, โครงสร้างโฟลเดอร์), จัดลำดับ, ตรวจงานทุกชิ้นก่อนส่งกลับหัวหน้า, ดูกำหนดเวลา 7 วันและเสนอตัดขอบเขตเมื่อเกินเวลา
- **Design (Game Designer + UX/UI + Art Direction):** ออกแบบกลไก, สมดุลอาวุธ/เศรษฐกิจ/ความยาก, flow หน้าจอ, HUD, สไตล์ภาพ, สี, เสียง, เอฟเฟกต์ ผลิต GDD ฉบับสั้นและ design tokens
- **Backend (Systems/Server):** ตรรกะฝั่งเซิร์ฟเวอร์, การตรวจสอบการยิง/ความเสียหาย, เศรษฐกิจ, เลเวล, ข้อมูลผู้เล่นและระบบเซฟ, matchmaking/รอบเกม, ป้องกันโกง
- **Frontend (Client/Gameplay Feel):** การควบคุม, กล้อง, การเล็ง/สโคป, ปืน (recoil, reload), อนิเมชัน, เสียง, VFX, UI/HUD, ความรู้สึกตอบสนอง
- **QA:** ทดสอบ, หาบัค, ทดสอบหลายผู้เล่น, ทดสอบประสิทธิภาพ, ทดสอบเซฟ, แก้และทดสอบซ้ำ

## 8.2 สายงาน (มี QA Gate ย่อยหลังทุกขั้น)
0. **START:** อ่านไฟล์นี้ + `PROJECT_MEMORY.md` + `DECISIONS.md` + `BACKLOG.md`
1. **หัวหน้า:** ALIGNMENT → Spec Card → รอยืนยัน
2. **รองหัวหน้า:** แตกงาน + เกณฑ์สำเร็จ + สัญญากลาง + ประเมินเวลา
3. **Design:** ออกแบบกลไก/UX/UI/ศิลป์ที่เกี่ยวข้อง (ส่งร่างให้ผู้ใช้ดูถ้าเป็นเรื่องที่เห็นภาพได้)
4. **Backend:** ระบบเซิร์ฟเวอร์/ข้อมูลตามสัญญากลาง
5. **Frontend:** ฝั่งผู้เล่นตามดีไซน์ เชื่อมกับ Backend
6. **QA:** ทดสอบ → แก้ → ทดสอบซ้ำ วนจนผ่านเกณฑ์
7. **หัวหน้าตรวจรับ:** เทียบกับ Spec Card ที่ผู้ใช้ยืนยัน ถ้าไม่ผ่านส่งกลับ
8. **CLOSE-OUT:** อัปเดต memory/CHANGELOG/BACKLOG + รายงานผู้ใช้
(ถ้าฟีเจอร์ไม่มีส่วนเซิร์ฟเวอร์ ให้รวมขั้น 4 กับ 5)

เหตุผลของลำดับ Design → Backend → Frontend: ฝั่งผู้เล่นต้องมีดีไซน์ให้ยึด และต้องรู้รูปแบบข้อมูลจากฝั่งระบบ ไม่งั้นต้องรื้อทำใหม่

# 9. AUTONOMY (ทำเองแค่ไหน)

| ประเภทงาน | การดำเนินการ |
|---|---|
| **เล็ก:** แก้บัคเล็ก, ปรับค่าตัวเลข, จัดโค้ด, เพิ่มคอมเมนต์ ย้อนกลับง่าย | ตรวจสอบละเอียด แล้วทำได้เลย + แจ้งสั้นๆ |
| **กลาง:** ฟีเจอร์ใหม่ในระบบเดิม | Spec Card → ยืนยัน → ทำ |
| **ใหญ่:** สถาปัตยกรรม, โครงสร้างข้อมูล/เซฟ, ระบบออนไลน์/เซิร์ฟเวอร์, ฟีเจอร์เทคนิคพิเศษ (ฟิสิกส์ละเอียด, แสงเงา, AI ศัตรู, สร้างแมปอัตโนมัติ), การเปลี่ยนเอนจิน, เผยแพร่, ระบบเงิน | แผนละเอียด + ทางเลือก + ผลกระทบ + รออนุมัติ **ทุกครั้ง** |
- ถ้าไม่แน่ใจว่าเล็กหรือใหญ่ ให้ถือว่าใหญ่
- เอเจนต์ **เสนอไอเดียได้** (ผู้ใช้อนุญาตให้ช่วยคิด USP/ฟีเจอร์) แต่ต้องถามก่อนลงมือทำเสมอ ไอเดียที่ยังไม่อนุมัติเก็บใน `BACKLOG.md` แยกสถานะ "เสนอ/อนุมัติ/ปฏิเสธ"
- เมื่อเสนอ ให้แย้งหรือชี้จุดอ่อนของไอเดียผู้ใช้ตรงๆ ถ้ามี พร้อมเหตุผล ตัดสินใจสุดท้ายเป็นของผู้ใช้

# 10. OPEN DECISIONS (ต้องถามผู้ใช้ตามจังหวะ ไม่ถามทั้งหมดทีเดียว)

เอเจนต์ถามทีละกลุ่ม (ไม่เกิน 5 คำถาม) เมื่อถึงขั้นที่ต้องใช้ พร้อมค่าแนะนำ บันทึกคำตอบลง `DECISIONS.md` (วันที่ + ทางเลือก + เหตุผล)

## กลุ่ม 1: ตอบก่อนเริ่มงาน (บล็อกการเริ่ม)
1. เทคโนโลยีและแพลตฟอร์ม (ข้อ 5) | แนะนำ: A เหตุผลในข้อ 5.2
2. มุมมองกล้อง: บุคคลที่หนึ่ง (FPS) หรือสาม (TPS) | แนะนำ: FPS สำหรับสไนเปอร์ให้ความรู้สึกเล็งเต็มที่ เว้นแต่แพลตฟอร์มที่เลือกมีข้อจำกัด
3. คำโปรย A หรือ B หรือเขียนเอง (ผู้ใช้ยังไม่ล็อก)
4. **CONCEPT GATE (ล็อกคอนเซ็ปต์ก่อน):** เสนอ 3 คอนเซ็ปต์เกม (แต่ละอันมีแนวเกม, คำโปรย 1 ประโยค, core loop, จุดต่างจากเกมอ้างอิง, ความเสี่ยงด้านเวลา) โดยหนึ่งในนั้นคือสไนเปอร์อารีนาตั้งต้น ให้ผู้ใช้เลือกหรือปรับ **ยังไม่ถามเรื่องอารมณ์/บรรยากาศ/ยุคสมัย/ฉาก/เนื้อเรื่อง/ตัวละคร/ศิลป์/เสียง จนกว่าคอนเซ็ปต์จะล็อก** เพราะผู้ใช้ยืนยันว่าเรื่องเหล่านี้ต้องตามเกมที่สร้างจริง หลังล็อกแล้วค่อยถามอารมณ์หลักพร้อมค่าแนะนำที่เข้ากับคอนเซ็ปต์
5. ปลายทางของโปรเจกต์: ให้เพื่อนเล่น / พอร์ตโฟลิโอ / ปล่อยสาธารณะ / หาเงิน (ผู้ใช้ยังไม่ได้เลือก) | ส่งผลต่อกฎแพลตฟอร์มและการวางระบบเงิน

## กลุ่ม 2: ก่อนทำ Design ของ MVP
6. จุดขายเฉพาะตัว (USP) ที่ต่างจาก Sniper Arena | ตัวอย่างทิศทางให้เลือก: (a) ระบบความเสี่ยง-ผลตอบแทน (พนันเงินรอบก่อนยิง) (b) แมปที่ทำลายได้/เปลี่ยนตามรอบ (c) ศัตรูบอทที่มีบุคลิกต่างกัน (d) ระบบสกิลที่เข้ากับสไนเปอร์ เช่น หน่วงเวลา/ตรวจจับ (e) ธีมโลกที่โดดเด่น ให้เสนอ 3–5 ทิศทางพร้อมข้อดีข้อเสีย
7. ระบบการเล่น: โหมดแข่งขัน (PvP) / ร่วมมือสู้บอท (PvE) / ผสม และรูปแบบรอบ (deathmatch, last-man-standing, wave)
8. อาวุธ: จำนวนและประเภทใน MVP, ปืนสไนเปอร์ทำความเสียหายแบบใด (นัดเดียวตายเสมอ หรือขึ้นกับจุดที่โดน), กระสุนแบบ hitscan หรือมีวิถี/แรงโน้มถ่วง/หน่วงเวลา | แนะนำ: เริ่มแบบ hitscan ที่ตรวจโดยเซิร์ฟเวอร์ แล้วค่อยเพิ่มวิถี
9. เศรษฐกิจและการพัฒนา: เงินได้จากอะไร, ร้านซื้อของ, เลเวล/สกิลทรี, ของที่ฟาร์มได้, ราคา/ความเร็วการเติบโต
10. เมื่อแพ้/ตาย: เกิดใหม่ทันที, เสียของบางส่วน, ผู้ชมรอ | แนะนำ: เกิดใหม่เร็ว+เสียเงิน/ไอเท็มเล็กน้อย เพื่อไม่ให้หงุดหงิดเมื่อเล่นหลายชั่วโมง
11. แมป: ขนาด, จำนวน, สไตล์ (สนามประลองเดียวก่อน) | แนะนำ: 1 แมป วางสมดุลแล้วค่อยขยาย
12. ตัวละคร: เลือกได้หรือตัวเดียว, การปรับแต่ง (skin) ใน MVP หรือไม่
13. เนื้อเรื่อง/ฉาก/ยุค/น้ำเสียง (ถามหลัง CONCEPT GATE ผ่านแล้วเท่านั้น ยุคสมัยต้องตามเกมที่ออกแบบ): ผู้ใช้ยังไม่ได้เลือก | แนะนำ: ฉากหลังบางๆ ก่อน (เกมแนวนี้ไม่ต้องพึ่งเนื้อเรื่อง) ประเด็นวัฒนธรรมไทยเป็นตัวเลือก
14. ระบบความก้าวหน้าและแรงจูงใจ: ปลดล็อก, ความสำเร็จ, อันดับ, ภารกิจรายวัน | ต้องตอบโจทย์ "ไม่น่าเบื่อหลังทำภารกิจครบ" (ดูข้อ 15)
15. การสอนผู้เล่นมือใหม่: ฝึกสอน/แนะนำทีละน้อย/สำรวจเอง | แนะนำ: ฝึกสอนสั้นๆ 1–2 นาทีที่เล่นจริง

## กลุ่ม 3: ก่อนทำศิลป์/เสียง/UI
16. สไตล์ภาพ (พิกเซล/ลอว์โพลี/การ์ตูน/เรียลิสติก/มินิมอล) + ภาพอ้างอิง + โทนสี | ผู้ใช้เคยชอบ "เรียบง่ายแต่มีคุณภาพ"
17. แหล่งแอสเซ็ต: สร้างเอง/แอสเซ็ตฟรีที่ไลเซนส์ถูกต้อง/เครื่องมือ AI (ดูข้อ 4)
18. เสียงและดนตรี: ความสำคัญ อารมณ์ | แนะนำ: เสียงปืน/ผลกระทบมีน้ำหนักก่อน ดนตรีรอง
19. HUD/UI: ธีม ปริมาณข้อมูล (ผู้ใช้ชอบเรียบง่าย)
